# عزل اختبارات مشاريع البرمجة

تحديث **15 نوفمبر 2026**: أصبح تنفيذ نسخة محدودة من ملفات Python وNode متاحًا عبر محول Docker محلي مثبّت بالهوية والصور. نُفّذت اختبارات حقيقية للإصلاح والموارد والإلغاء والتنظيف. يبقى تنفيذ شيفرة المشروع على مضيف Windows محظورًا؛ لا بديل تلقائي عند غياب المحرك أو تعذّر التحقق منه. هذه قدرة جزئية، وليست بيئة بناء عامة لكل مشروع أو شهادة سلامة للشيفرة.

## الإعداد وحد الثقة

الإعداد التشغيلي هو `isolated-workers.json` داخل `RIWAQ_DATA_DIR`. هذا ملف خادمي محلي صارم يثبت مسار Docker وبصمته، endpoint محليًا، هوية المحرك وصور التنفيذ بالـimage ID. لا يُقبل مساره أو محتواه من مهمة أو نموذج. `config/coding_capabilities.json` سجل ملاحظات؛ تعديله ليس إذنًا لتشغيل المضيف. لا متغير بيئة يفتح fallback أو يضيف شبكة أو اعتماديات للمهمة.

يفحص المحول المحرك والصورة وسياسة الحاوية لكل تشغيل، ثم ينقل البايتات المختارة عبر stdin إلى bootstrap ثابت. السياسة تشمل شبكة `none`، مستخدمًا غير root، جذرًا للقراءة فقط، حذف capabilities، `no-new-privileges`، seccomp الافتراضي، منع host mounts والأجهزة، CPU واحدًا، حد PIDs يبلغ 64، وtmpfs محدودًا 64 MiB. حد الذاكرة وswap متساويان، فلا يضاف swap خارج سقف الطلب. تُفحص سياسة الحاوية قبل بدء شيفرة المشروع، ثم يُراقب الإلغاء والتفويض والوقت والمخرجات والتنظيف.

تشارك الحاويات نواة Linux الخاصة بمحرك Docker، ويظل Docker Desktop والمحرك والصورة وbootstrap أجزاء موثوقة. هذه ليست شهادة مقاومة لكل ثغرة في النواة أو المحرك، ولا حماية من مسؤول النظام أو برنامج خبيث يملك حساب Windows نفسه. [أمن Docker](https://docs.docker.com/engine/security/)، [سياسة seccomp](https://docs.docker.com/engine/security/seccomp/)، [خيارات تشغيل الحاويات](https://docs.docker.com/engine/containers/run/).

## عقد التكامل والنتائج

توفر `backend/coding_sandbox.py` مسارين منفصلين:

- `run_tests(snapshot_root, request, ...)` هو عقد المنع القديم: لا يفتح المجلد ولا ينشئ عملية. يبقى مستخدمًا عندما لا يوجد إعداد صالح.
- `run_snapshot(files, request, stop, authorize, progress)` يقبل بايتات محدودة سبق تفويضها، ويلزم callback يعيد فحص التفويض. وحده ينتقل إلى محول الحاوية.
- `status()` لا يشغّل Docker أثناء الاستطلاع. الإعداد الصالح يعطي `mode: "isolated_configured"` و`can_request: true`، مع بقاء `available/tested` غير معتمدين كفحص حي. كل تنفيذ يحتاج تحققًا جديدًا؛ فشل التنظيف يمنع التنفيذ التالي حتى التعافي.

`TestRequest` يقبل `python_unittest` أو `node_test`، ومن 1 إلى 20 هدفًا نسبيًا صريحًا، ومهلة 1–120 ثانية، وذاكرة 128–2048 MiB. المخرجات حتى 64 KiB. تُرفض المسارات المطلقة والانتقال `..` وglob وصيغة الأوامر ومسارات الأسرار والأدوات والحقول الإضافية و`network: true` و`install_dependencies: true`. لا shell حر أو npm lifecycle أو تثبيت اعتماديات.

في `/coding/tasks/{id}/checks` تُحفظ نية الفحص ونسخة البصمات ومفتاح منع التكرار قبل التشغيل. إذا كان الاقتراح لم يُطبّق تُفحص نسخته المقترحة؛ وإلا تُفحص الملفات الحالية المختارة. تغيّر المصدر أثناء الفحص يجعل الإيصال `stale`. سحب المنحة أو انتهاء الجلسة يبطل التفويض؛ لا يُعاد نشر الخرج في مهمة فقدت صلاحيتها.

الإيصال يميز الانتظار والتشغيل والاكتمال والفشل والحجب والإلغاء والمهلة والانقطاع وفشل التنظيف بحسب النتيجة الفعلية. الأسماء الدقيقة والحقول في التقرير المحفوظ هي المرجع. `tests_passed` و`test_count` يبقيان `null`، و`test_count_verified: false`؛ الخرج النصي الصادر عن كود المشروع غير موثوق. النجاح التشغيلي هو اكتمال المراقب وخروج صفر والتحقق من السياسة والتنظيف، ولا يساوي صحة دلالية.

عندما تتضمن مهمة `apply_local` طلب `test_request`، لا يطبق المسار الفرق إلا بعد `status: "completed"` و`exit_code: 0` و`policy_inspected: true` و`cleanup_verified: true`، ثم إعادة فحص تفويض الملفات وبصماتها. إن حُجب الفحص أو فشل يبقى الاقتراح للمراجعة. المهمة التي لا تطلب اختبارًا تحتفظ بعقد التعديل المصرح به وفحوص البنية والبصمات؛ لا تُسجل اختبارًا لم يحدث.

عند غياب الإعداد أو عدم سلامة الحدود يعود تقرير `blocked` مع `executed: false` و`tests_passed: null` و`host_fallback: false` و`automatic_download: false`. لا يحوّل العميل هذا إلى نجاح أو إلى فشل اختبارات المشروع؛ الاختبارات لم تبدأ أصلًا.

## الانقطاع والتعافي وما لم يُعمّم

تُحفظ هوية الحاوية قبل تمرير المصادر وتشغيلها. التعافي ينظف الحاوية المملوكة المسجلة بعد مطابقة الهوية والصورة، ولا يعيد تنفيذ المهمة. إثبات تنظيف حاوية متروكة موجود في التقرير المشار إليه؛ قبول التزامن بين العمليات وقفل نسخة الخدمة له فحوص مستقلة ولا يُستنتج من هذا التقرير وحده.

`visual_runner` وWindows Job Object ومهلة Python والمجلد المؤقت وGit worktree أدوات إشراف، وليست عزلًا لشيفرة غير موثوقة. WSL العادي أيضًا ليس بديلًا عن سياسة الحاوية، إذ يمكن أن يتيح أقراص Windows وأدواته. [توثيق WSL](https://learn.microsoft.com/en-us/windows/wsl/faq).

استُخدم محول Docker كذلك لمسار استخراج PDF/DOCX القديم وHTML/PDF العام باختبارات أصلية محلية؛ راجع [مصفوفة الاستخراج الفعلية](../reports/completion-parser-live.json). هذا لا يشمل تلقائيًا جميع مسارات PDFium وOCR والصور والصوت والفيديو. لا ينبغي عرض كل worker في رواق على أنه معزول بسبب نجاح هذه المجموعة.

## إعادة التحقق

```powershell
.venv/Scripts/python.exe -X utf8 -B -m pytest tests/test_coding_sandbox.py tests/test_isolated_worker.py tests/test_coding_checks.py -q -p no:cacheprovider
```

هذه اختبارات عقود وسلوك خادمي؛ بعضها يستخدم Docker محاكى، ولا يغني نجاحها عن تقارير التشغيل الحقيقي المذكورة أعلاه. الفحوص الحقيقية تحتاج المحرك المحلي والإعداد المثبت، وتُشغّل أمثلة أصلية محدودة داخل الحاوية فقط. تشغيل اختبارات رواق الداخلية الموثوقة لتطوير المنتج منفصل عن اختبار مشروع المستخدم. المراجعة الأمنية البشرية المستقلة وقبول Stage8 لم يكتملَا، ولا يفتحهما نجاح Docker أو رمز خروج صفر.
